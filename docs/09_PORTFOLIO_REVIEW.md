## 2. 기술적 한계점 & 원인 분석 (솔직한 회고)

### 2.1 Timestamp / 시계열 데이터 한계

**문제**: 모든 시간 기반 계산(PPS, 지터, 가용성)이 `datetime.now()`에 의존

```python
# packet_store.py — PPS 계산
def get_pps(self) -> int:
    one_sec_ago = datetime.now() - timedelta(seconds=1)
    return sum(1 for r in self._records if r.timestamp >= one_sec_ago)
```

**구체적 영향**:

| 지표      | 왜곡 원인                                                                                            | 실체                                    |
| --------- | ---------------------------------------------------------------------------------------------------- | --------------------------------------- |
| PPS       | 패킷 수신 시각(`datetime.now()`)으로 측정하므로, **네트워크 지연이나 처리 지연이 PPS에 직접 반영**됨 | 실제 VIC 송신 PPS와 불일치 가능         |
| 지터      | `datetime.now()` 간격 차이 = **수신 지터**(= 네트워크 지터 + 처리 지터 혼합)                         | 순수 네트워크 지터를 분리할 수 없음     |
| 가용성    | `datetime.now()` 기반 1.5초 타임아웃으로 연결 상태 판정                                              | 처리 지연 시 false disconnect 발생 가능 |
| 패킷 손실 | 시퀀스 번호 4-bit 순환(0~15)으로 wrap-around 후 gap 계산                                             | 16개 이상 연속 손실 시 감지 불가        |

**근본 원인**: ICD 헤더의 timestamp 필드가 절대 시각이 아닌 카운터/시퀀스 용도이므로, **VIC 측 송신 시각을 알 수 없음**. 결과적으로 one-way delay, 진짜 네트워크 지터 등을 정확히 계산하는 것이 원천적으로 불가능했음.

**이상적 해결책 (만약 가능했다면)**:

- NTP/PTP 시각 동기화 후 ICD 헤더 timestamp를 절대 시각으로 변환
- one-way delay 산출 → 진짜 네트워크 지터 분리
- 고정밀 타이머(`time.perf_counter_ns()`) 활용으로 처리 지연 분리

### 2.2 메시지 코드별 임계값 미분리 — ML 데이터 오염

**문제**: 현재 Rule Detector와 ML 모델이 **모든 msg_code를 하나의 데이터 스트림으로 처리**

```python
# rule_detector.py — 단일 임계값
DEFAULT_THRESHOLDS = {
    "jitter_max_ms": 50.0,    # 모든 msg_code 공통
    "pps_min": 50,            # 모든 msg_code 공통
    "loss_rate_max": 5.0,
    "checksum_fail_max": 10.0,
}
```

**구체적 영향**:

| msg_code        | 특성                                   | 문제                             |
| --------------- | -------------------------------------- | -------------------------------- |
| 0x01 (상태보고) | ~1 pps, 87B 페이로드, 풍부한 운용 정보 | 유일하게 상세 분석 가능한 메시지 |
| 0x10 (하트비트) | 주기적, 소형, 연결 확인용              | 지터/PPS 패턴이 0x01과 상이      |
| 0x25 (확장상태) | 비정기적, 정보 제한적                  | 학습 데이터에 노이즈로 작용      |
| 0x40 (장치상태) | 비정기적, 정보 제한적                  | 학습 데이터에 노이즈로 작용      |

**데이터 오염 시나리오**:

1. **학습 시**: 0x01, 0x10, 0x25, 0x40이 뒤섞인 통계로 Isolation Forest가 학습 → 각 코드의 고유 패턴이 아닌 **혼합 분포**를 학습
2. **예측 시**: 0x10 하트비트가 일시적으로 증가하면 PPS 급등 → ML이 **false positive** 판정
3. **방향 전환(toggle direction)**: VIC→OCS / OCS→VIC 전환 시 패킷 스트림이 완전히 바뀜 → **기존 학습 데이터와 분포가 달라져 모델 무효화**
4. **연결 토글(toggle connection)**: 캡처 중단/재개 시 PPS 0 → 정상 복귀 구간이 **이상 탐지에 혼란** 유발

**`reset_stream_state()`로 일부 대응했지만 근본 해결은 아님**:

```python
# packet_store.py
def reset_stream_state(self) -> None:
    """스트림 상태만 리셋 (방향 전환 시 지터 오염 방지)."""
    self._metrics.reset()
```

→ 지터 계산의 이전 상태는 리셋되지만, **ML 모델의 학습된 분포 자체는 오염된 상태로 유지됨**.

**이상적 해결책**:

- msg_code별 독립 파이프라인: `FeatureExtractor[0x01]`, `MLPipeline[0x01]`처럼 메시지 코드별 분리
- 방향 전환 시 ML 모델 자동 재학습 또는 방향별 모델 유지
- 연결 토글 구간을 학습/예측에서 제외하는 **데이터 필터링 로직**

### 2.3 ML 성능 최적화 미진 — 단순 도입에 그친 아쉬움

**현재 구현 수준**:

```
[데이터 수집] → [7차원 특성 추출] → [StandardScaler] → [Isolation Forest] → [Score → 이상 판정]
```

**놓친 성능 최적화 방법론들**:

| 카테고리      | 기법                                      | 기대 효과                | 미적용 사유                          |
| ------------- | ----------------------------------------- | ------------------------ | ------------------------------------ |
| **전처리**    | 이동 평균/지수 평활 (EMA)                 | 노이즈 감소, 안정적 특성 | 시간 부족                            |
| **전처리**    | 시간 윈도우 집계 (5s/30s/60s 다중 윈도우) | 다중 시간 축 패턴 포착   | 구조 복잡도 증가 우려                |
| **특성 공학** | 변화율(derivative), 자기상관(ACF) 특성    | 추세 변화 민감도 향상    | 도메인 지식 부족                     |
| **특성 공학** | msg_code별 PPS 비율 특성                  | 메시지 분포 이상 탐지    | msg_code 정보 제한                   |
| **모델**      | Sliding Window Isolation Forest           | 시간 변화 적응           | sklearn 기본 모델 한계               |
| **모델**      | AutoEncoder (비지도)                      | 복잡한 비선형 패턴 학습  | 폐쇄망 배포 제약 (PyTorch 도입 부담) |
| **모델**      | 적응형 임계값 (Adaptive Threshold)        | 환경 변화 자동 대응      | 구현 복잡도                          |
| **앙상블**    | 시간대별 모델 (주간/야간)                 | 운용 패턴별 정밀도 향상  | 데이터 부족                          |
| **평가**      | 합성 이상 데이터 + Precision/Recall 측정  | 정량적 성능 평가         | 실제 이상 데이터 없음                |
| **후처리**    | 연속 N회 이상 시 알람 (디바운싱)          | false positive 감소      | 시간 부족                            |

**특히 아쉬운 점 — 신뢰도 향상을 위한 간단한 기법들조차 미적용**:

1. **이동 평균 기반 스무딩**: `quality_score`에 EMA를 적용하면 순간적 노이즈 제거 가능
2. **다중 시간 윈도우**: 5초/30초/60초 윈도우별 PPS 평균을 특성으로 추가하면 짧은 스파이크와 지속적 저하를 구분 가능
3. **디바운싱**: 연속 3회 이상 anomaly 판정 시에만 알람 → false positive 대폭 감소
4. **정량 평가 체계 부재**: 합성 이상 시나리오(sudden PPS drop, gradual jitter increase 등)를 만들어 Precision/Recall/F1을 측정하지 못함

## 5. 포트폴리오 한줄 요약 (다양한 용도)

### 이력서용 (1~2줄)

> 무인지상차량(UGV) VIC↔OCS 간 UDP 통신을 실시간으로 모니터링하는 대시보드 시스템을 단독 설계·구현. 4계층 아키텍처(Pipeline/Store/Service/UI), Isolation Forest + Rule-based 앙상블 이상 탐지, 7개 KPI 실시간 시각화. Python ~6,170줄, 52개 테스트, 8주 개발.

### 블로그 제목 후보

1. "실시간 통신 모니터링에 Isolation Forest를 도입한 이야기 — 한계와 교훈"
2. "datetime.now()의 함정: 실시간 시계열 분석에서 시각 동기화가 중요한 이유"
3. "폐쇄망 환경에서 ML 이상 탐지 시스템을 구축하며 배운 것들"

### 면접 핵심 어필 포인트

1. **아키텍처 설계 역량**: 모놀리식이 아닌 4계층 + SRP 서비스 분리를 8주 안에 설계·구현·검증
2. **ML 실무 적용 경험**: 이론이 아닌 실제 운용 환경의 제약(폐쇄망, 데이터 부재, Cold Start)에 대응한 앙상블 시스템
3. **솔직한 한계 인식**: "완벽한 시스템"이 아님을 인지하고, 구체적 개선 방향을 제시할 수 있는 엔지니어링 마인드
4. **문서화 습관**: 코드와 동등한 수준의 문서(11개 파일)를 유지하며 개발한 경험
